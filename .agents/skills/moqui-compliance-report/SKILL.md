# moqui-compliance-report: compliance reports as Moqui wiki pages

The content of a report comes from the norms and the database (`moqui-ot-risk-assessment`,
`moqui-norm-requirements`, `moqui-norm-search`); this skill is about where it goes and how it renders. A report
section exists because a norm item requires it: cite the item id next to the heading.

## Page types (framework `MoquiDefaultConf.xml` template renderers)

| Extension (`wikiType`) | Rendering | Use for |
| --- | --- | --- |
| `md` | Markdown (flexmark 0.64.8, tables and TOC extensions) | a report written once and versioned: risk-assessment results, CRS, threat intelligence |
| `md.ftl` | Markdown **first**, then FreeMarker on the resulting HTML | prose with a few live numbers or tables |
| `html.ftl` | FreeMarker only | pages that are mostly loops over records |

### Rules for `.md.ftl` (verified on the renderer, `FtlMarkdownTemplateRenderer`)

Markdown is parsed before FreeMarker runs, so:
- an FTL directive (`<#list>`, `<#if>`, `<#assign>`) or FTL comment (`<#-- -->`) in Markdown text is escaped to
  `&lt;#list&gt;` and breaks or shows as text: put every directive **inside an HTML block**, a block whose first line
  starts with an HTML tag such as `<div>` or `<table>`, and keep the block free of blank lines;
- Markdown tables and lists cannot be generated by a loop: write the table in HTML (`<table class="table">`) with the
  `<#list>` inside;
- `${...}` in a Markdown link target is percent-encoded and breaks: write such links as HTML `<a href="${...}">`;
- `${...}` in plain text and in headings works;
- use HTML comments `<!-- -->` inside the HTML block for notes; they reach the browser, so no secrets.

### FreeMarker in Moqui (2.3.35)

- `ec` is in the context: `ec.entity.find(...)`, `ec.service.sync().name(...).parameters(...).call()`,
  `ec.web.parameters` for URL parameters (`?projectId=...`), `ec.user.nowTimestamp`.
- No Groovy syntax: no `list*.field`, use `?map(x -> x.field)?sequence`, `?filter(...)`, `?sort_by("field")`.
- Prefer one service call or a few finds per page; a page renders on every view.

## Wiki spaces and publishing

- A space: `WikiSpace` with `rootPageLocation` `dbresource://WikiSpace/<ID>.md` (the default of
  `org.moqui.impl.WikiServices.create#WikiSpace`); the id is 3 to 8 characters, letter first. Pages are stored in the
  database resource store, each update is a version (page history, compare, publish).
- **Security**: `.ftl` pages run server-side with the full `ec` of the viewer. Every space holding report or template
  pages has `restrictUpdate=Y` and `WikiSpaceUser` rows with `allowUpdate=Y` only for the report authors; set
  `restrictView=Y` for classified reports (ZCR 5.13 requires a classification). With `allowAnyHtml` not `Y`, only
  `wikiType` `html` is filtered (Jsoup relaxed); `md` and `.ftl` pages are stored as written.
- Publish **from a terminal on the host** with `scripts/wiki_publish.sh` (form login, session token, then the wiki
  screen transitions):

```sh
scripts/wiki_publish.sh space   CMPRPT "Compliance reports"
scripts/wiki_publish.sh protect CMPRPT EX_JOHN_DOE                         # restrictUpdate=Y + authors (UserAccount ids)
scripts/wiki_publish.sh page    CMPRPT RiskAssessment md filled-risk-assessment.md
scripts/wiki_publish.sh page    CMPRPT ProjectStatus md.ftl assets/norm-project-status.md.ftl
scripts/wiki_publish.sh get     CMPRPT ProjectStatus projectId=100000      # rendered text and template errors
```

  No screen manages `WikiSpaceUser`: `protect` loads it with Tools > Entity > Data Import, which does not check that
  the `userId` exists. A transition answers 302 also when validation fails: always `get` the page after publishing. The
  services themselves (`update#WikiPage`, `create#WikiSpace`) are not callable through MCP `run_service` for a normal
  user (artifact authz), and the `skills-python` sandbox has no network access to Moqui; in a LibreChat chat, write the
  filled Markdown/FreeMarker pages in the workspace (`write_file`) or as an artifact so `wiki_publish.sh` can publish
  them on the host. Pages are viewed at `/apps/hm/wiki/<space>/<page>`.

## Templates (`assets/`)

| File | Type | Content |
| --- | --- | --- |
| `risk-assessment.md` | md | sessions and participants, archived inputs, ZCR 1 SUC and access points, ZCR 2/4 initial risk vs tolerable, ZCR 3 zones with the grouping rule, ZCR 5 per-zone threat table (unmitigated and residual columns kept apart), open decisions |
| `crs.md` | md | the CRS of ZCR 6.2-6.9; the zone characteristics table has the rows of `4.7.5.1` |
| `threat-intel.md` | md | threat source by the four elements of `4.6.2.2`, attack steps with technique labels and the FR/SR countering them, what the source does not know, relevance to the SUC |
| `norm-project-status.md.ftl` | md.ftl, live | `?projectId=`: requirements by status, milestones per norm with their tasks |
| `zones-conduits.html.ftl` | html.ftl, live | `?sucProductId=`: zones and conduits (function levels) of the SUC with members and roles; warns when none exist |

Fill a static template with data read from the database in the same session; keep `{placeholders}` out of a
published page (search for `{` before publishing).

## Report rules

- Every requirement, countermeasure and decision cites its norm item (agreement id and item id); a third-party
  method or a threat report is cited as a source, never as the requirement.
- Licensed norm text (IEC, ISO, EN): quote in internal pages only; in a page shared outside, cite and paraphrase.
- Record what is unknown as unknown (initial access not known, likelihood not rated yet), never fill gaps with
  assumptions presented as findings.
- Approval (ZCR 7) and requirement status (approved / rejected) are set by people; a report states who and when.
